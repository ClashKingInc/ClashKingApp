# Stats data audit

Audit date: 2026-09-22. This is a source-level audit of the Expo Stats feature, the API contracts and Worker queries, the Timescale schema, and the Tracking writers. The local API at `127.0.0.1:8787` was not running during the audit, so this document makes no claim about current local row counts or production coverage.

## What is trustworthy today

### Implementation following this audit

The findings below describe the pre-redesign baseline. The local Expo changes now clamp multi-day army requests to 10 results, preserve unknown army player counts, date-label the newest Legend player sample, retain filter access after empty responses, and show the actual client refresh time. Battle performance has one primary hit rate, compact secondary statistics, authentic star distributions, and selectable date/percentage charts that break across missing observations. Army and season summaries use compact cards instead of repeating full charts; World distributions expose counts, shares, and expandable category coverage rather than silently dropping rows. These are local source/test changes, not production deployment or visual-device verification.

The backend work described below remains a concrete backlog: server coverage/freshness metadata, scheduling/backfilling the experimental Legend arrays, equipment-adoption denominators, current experience facts, and season-scoped CWL roster aggregates. No production tracking or schema migration was activated by this UI redesign.

World locations now also join optional official location metadata for names and country flags; metadata failure preserves the underlying counts. Capital league names and CWL artwork use canonical identities, with translated display names kept separate from asset paths.

The battle performance math is generally sound: samples are attacks, star rates use attacks as the denominator, averages are attack-weighted, and army/item triple rate uses that army or item's uses. The largest problems are request/display integration rather than arithmetic:

1. The audit found that Expo's default Armies request asked for `limit=25` over 30 days while the API allows at most 10 multi-day results. `StatsArmiesQuery` now clamps to 10 for multi-day ranges and 250 for a single day.
2. The current Armies sheet renders only supported minimum-sample, cohort, and sort controls. Town hall, league, exclusions, and quantity filters remain latent provider/model state but are not visible; the public army endpoint has no corresponding query fields except hero/equipment presence IDs.
3. Legend Items labels the oldest returned day's player count as the range's player value. The API returns days descending, but the screen reads `items.at(-1)`.
4. New Legend troop/spell/siege/equipment-pair/pet-combo data is experimental local data. The scheduled closeout still writes only heroes, pets, equipment, and pet assignments; schema defaults make the other arrays look like legitimate empty usage in environments that have not been manually rebuilt.
5. World charts expose stored-tracker distributions, not worldwide Clash populations. They have no server freshness timestamp, total denominator, coverage statement, or location names, and the Clans screen currently reduces location rows to the number of distinct IDs while discarding every location's clan count.

## Data path and freshness

| Surface | Authoritative source and lifecycle | Freshness visible to Expo |
| --- | --- | --- |
| Ranked | Attack-perspective `battles_ranked`, joined to `ranked_league_group_members` for the membership's tournament period | None. The response returns the requested range, not source freshness or coverage. |
| Armies and Legend items | Completed 05:10 UTC Legend days in `legend_daily_stats` and `army_family_daily_stats` | None. Missing days are omitted silently. There is no completed-through date or requested/available-day count. |
| Regular War | Uploaded `war_archive_packs` plus still-pending archived wars in the same database snapshot | None. The query doesn't expose pack coverage or completed-through time. |
| CWL | Uploaded CWL archive histograms plus pending wars; the API fails instead of returning a filtered result when coverage or requested league attribution is incomplete | None on success. A coverage failure becomes a generic client error. |
| World players | `townhall_counts` and `api_league_tier_counts`, both derived from tracked `basic_player` rows | Tracking refreshes these materialized views on a 30-minute cadence, but `refreshed_at` is not selected by the endpoints. |
| World clans | CWL counts are the `war_league_counts` materialized view; location and capital league counts query current `basic_clan` rows directly | No endpoint timestamp. These three cards can represent different effective snapshots. |

The Expo provider adds only a client `updatedAt` timestamp after a successful fetch. A section remains cached for the provider's lifetime and does not refetch when revisited. Manual refresh keeps old data after failure, which is useful, but the badge says only “Updated”; it does not show when the data was fetched, when the source was completed, or that retained data is stale.

All item and army usage rates currently use `uses or family attacks / total cohort attacks`. That is correct for attack presence. Triple rate uses `triples / uses`, which is also correct. Neither number is an eligible-population preference rate; TH, unlock state, and hero association need separate denominators rather than a relabeling of the existing values.

The `/v2/counts` global endpoint already returns overall tracked player/clan/war counters, but the Stats repository does not request it. It can support top-level tracked totals after its `refreshed_at` is also exposed; it still must not be labeled as the worldwide Clash population.

## Empty, partial, and stale behavior

- Performance sections become globally empty when `metrics.available` is false. This is consistent with current API responses, but numeric parsing maps missing/invalid metric fields to zero, so a contract regression can look like a genuine 0% result instead of failing loudly.
- Legend Items is empty only when no day rows exist. Required arrays and optional new arrays both decode missing fields to empty arrays, so “unsupported/not backfilled” and “zero uses” are indistinguishable.
- Armies never enters the provider's empty state. An empty result is rendered as a local filtered-empty message, even when no server data exists for the selected days/cohort.
- Player/Clan World sections remain “data” if any parallel endpoint has rows. Empty companion charts render blank bars without a section-level explanation.
- Parallel World requests use `Promise.all`; one failed count endpoint removes the entire Players or Clans section even when the other distributions succeeded.
- The provider cache has no TTL or foreground invalidation. The only source of refresh is a new provider, changed dates, or explicit refresh.
- Requested date labels are shown from provider state, while returned `dateRange` and actual available Legend days are ignored. A user can therefore see a full requested window around a partial underlying result.

## Recommended order

1. **Make the existing UI honest and loadable.** Retain the new Armies limit clamp and nullable-player handling, remove latent unsupported army filter state, fix the Legend latest-day selection, relabel family and attack-presence concepts, and show real client refresh time.
2. **Add coverage before adding charts.** Extend battle responses with requested/available days and completed-through time; extend grouped counts with `total` and `refreshedAt`; add an item-metadata capability/backfill boundary. These fields stop missing data from becoming a plausible zero.
3. **Use existing authoritative aggregates.** Add the existing ranked tier statistics to Meta, use location catalog names plus actual clan counts, and use global tracked counters where a tracked-total headline helps.
4. **Promote experimental Legend metadata deliberately.** Run the new columns/writer through normal schema deployment, scheduled closeout activation, and historical backfill verification before production UI treats them as complete. The scheduled `FinalizeLegendCloseout` path currently remains on the legacy field set by design.
5. **Build coming-soon endpoints only with declared populations.** Equipment adoption can use observed detailed profiles; experience needs a new current-profile fact or a leaderboard-only label; CWL roster size must use season registration rather than current clan membership.
