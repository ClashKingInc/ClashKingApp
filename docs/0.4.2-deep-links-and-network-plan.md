# Deep links, images, and poor-network support

Planning snapshot: September 3, 2026. The deep-link proposal below is superseded by [the implemented route reference](deep-links.md), including its HTTPS deployment prerequisites. The image and adaptive-network sections remain the original planning snapshot. Cache fixes described as implemented are in the local checkout, not a deployed release.

## Deep links

Today the native handler actually opens player and clan links using query-string tags. War links still show “coming soon”; the runtime ignores HTTPS links, and web does not hydrate arbitrary feature URLs. Having a route name in the navigation manifest does not make it a working external link.

Use a single typed route registry for navigation, sharing, widgets, push destinations, browser history, and cold-start links. Canonical share links should be `https://app.clashk.ing/...`; retain `clashking://player?tag=%23TAG` and the equivalent clan links. In paths, use uppercase tags without `#` so they cannot become URL fragments. Query values must be URL-encoded.

There should not be share links for ephemeral confirmation dialogs, temporary drag state, secret tokens outside their dedicated auth flows, or destructive actions. Feature-disabled or unavailable destinations should produce a helpful fallback, not a broken screen.

### Implementation order

1. Build and test the parser/serializer and typed route registry. Validate tags, tabs, dates and numeric ranges; support old custom links without duplicating navigation logic.
2. Route links through bootstrap/auth. Keep the destination while signing in, then open it once. Opening a private account route still requires ownership/authorization; a URL is not permission. Deduplicate warm-start delivery and redact auth query strings from logs.
3. Connect all screens to initial route state and browser history. Add proper Expo web route handling, direct refresh support and back/forward behavior; the present export has only four static routes, so this is real work, not just adding URL constants.
4. Add Apple Universal Links and Android App Links, including domain association files and Android production certificate fingerprints. Verify cold/warm native launch, logged-out continuation, PWA/browser fallback and invalid links when visual/device testing is authorized.
5. Wire widget taps to their **saved instance entity**. War widget → that clan's current war/CWL; upgrade widget → that saved player's upgrade tracker. Optional subtargets can open a round or tracker tab. A refresh control remains refresh, not navigation.

Estimate: roughly 3–5 engineering days for the registry, core routes and widgets; another 2–4 for the complete screen inventory and platform verification, depending on historical-ID availability. These are planning estimates.

## AVIF and caching

Bulk replacement is feasible, but blind `.png` → `.avif` URL replacement is unsafe. First generate real AVIF variants in the assets repository, publish a manifest of available variants, and switch the shared image resolver. The current iOS dependency installation includes the AVIF decoder; Expo Image documents AVIF support, but native widget image loaders need their own compatibility checks, especially on older Android versions. Keep a supported fallback for those consumers. [Expo Image documentation](https://docs.expo.dev/versions/latest/sdk/image/)

Keep launcher icons and required splash assets in platform-supported formats, and keep SVGs where they already work well. For tiny flat-color/transparent images, compare optimized WebP/PNG against AVIF rather than assuming AVIF always wins. For larger artwork, combine format conversion with correctly sized thumbnails; downloading a large original for a small card wastes bytes regardless of format. Measure decode time as well as encoded size on a low-end phone.

Rough effort: 1–2 days for representative variants, manifest/resolver integration and fallback; another 2–4 days for pipeline rollout and native/widget compatibility checks. No bulk conversion is included in the current edits.

### What the app actually does now

| Layer | Verified behavior | Consequence |
| --- | --- | --- |
| Shared app image component | `MobileWebImage` defaults to Expo Image's `disk` cache policy and allows downscaling. URL-resolution memo holds up to 512 entries; failed URLs have a 20-second suppression window. | This is a disk-cache request, not a promise of permanent storage or one universal TTL across OS/browser implementations. |
| Image retry | Asset-host failures get one alternate query-string retry. | A weak connection can download the same resource under two cache keys; include this in the byte/retry audit. |
| Native static game metadata | Document-directory JSON cache with six-hour freshness; stale cached data can be used while checking the remote version. HEAD/Last-Modified avoids unchanged downloads. | Repeat launches are much cheaper; first-install behavior still depends on network access. |
| Web static game metadata | Previously no persistent file store. Current edits add a dedicated Cache Storage store, six-hour freshness and best-effort background refresh. | Cached metadata survives page reloads and can be used offline; storage denial/quota does not fail the live request. |
| PWA shell | Build-fingerprinted service-worker cache; hashed web assets have one-year immutable headers; service worker itself is no-cache, manifest is one hour. | A new build updates the shell. Current edits preserve unrelated caches, skip private/no-store responses and tolerate cache failures. |
| Mutable public metadata CDN | Both `static_data.json` and `translations.json` returned `max-age=86400, stale-while-revalidate=604800`, with ETag and Last-Modified. | App freshness and HTTP freshness are separate; a six-hour app refresh can still receive an HTTP-cached document. |
| Sample badge | `badges.clashk.ing/2VC0Q9LV.avif`: 1,837 bytes, `max-age=86400,s-maxage=86400`. | Existing badge AVIF is small and cached for a day. This sample is not a benchmark of every badge. |
| Sample brand PNG | `assets.clashk.ing/logos/crown-arrow-dark-bg/ClashKing-1.png`: 226,028 bytes, ETag/Last-Modified but no explicit Cache-Control. | That response should get an intentional caching policy; don't assume all assets are already immutable. |

Public HEAD responses were inspected September 3 locally / September 4 UTC. The metadata Content-Length values were 2,060,724 and 2,382,731 bytes; these are response representation sizes, **not measured compressed transfer bytes**. Both samples reported `cf-cache-status: DYNAMIC`, so origin headers alone do not prove Cloudflare edge-cache hits.

For assets that truly never change, publish content-hashed/versioned filenames with `Cache-Control: public,max-age=31536000,immutable`. Give the small manifest a short lifetime and validators so it can point to new filenames. Do not put year-long immutable caching on an image URL whose contents get overwritten, or on personalized API data. Keep stale cached images during offline reads; bound disk use and let the OS reclaim its cache.

## Poor-network benchmark and adaptive behavior — plan only

There is no measured “minimum supported connection” yet. A warm cached app and a first install are very different, and a single bandwidth number omits latency, packet loss and disconnects.

The current web export contains a roughly **15 MB uncompressed entry bundle**. That is an immediate investigation target along with the two large metadata files; changing image formats alone will not solve cold PWA launch. Inspect eager screen imports, bundled locale catalogs, and the full third-party license inventory as possible contributors, then measure actual compressed transfer and parse time before changing loading boundaries. The native store app already contains its JavaScript bundle; Metro development bundle traffic must not be used as a production benchmark.

### Test matrix

Run the same flows on an iPhone, low-end Android and production PWA export. For every profile, test a cold install/cache, warm cache, returning authenticated session and 1/10/50 linked accounts.

| Profile | Download/upload | RTT / loss | Purpose |
| --- | --- | --- | --- |
| Baseline | Unthrottled | Recorded, not assumed | Establish overhead without shaping |
| Constrained | 1 Mbps / 250 Kbps | 300 ms / 0% | Common slow mobile connection |
| Poor | 256 / 64 Kbps | 800 ms / 2% | Prioritize useful content over decoration |
| Severe | 64 / 16 Kbps | 1,500 ms / 5% | Find practical failure limits |
| Interrupted | Profile above, then 30 s offline | Reconnect afterward | Retry/cancellation and stale-data behavior |
| Offline | No network | Cold vs cached | Document what genuinely remains usable |

Use iOS Network Link Conditioner or a controlled network/proxy, equivalent shaping for Android, and browser tools for PWA-specific tests. Shaping must cover all hosts: API, assets, badges and OTA downloads. Apple recommends testing adverse network conditions rather than relying on an ideal development connection. [Apple: networking for constrained networks](https://developer.apple.com/videos/wwdc2019/422/)

Record time to useful screen, interaction readiness, first clan/war data, error recovery, bytes and request count by **images / JSON / JS / fonts / OTA**, cache hits, concurrent requests, retries, timeouts, image decode and JS parse time. Use p50/p95 from repeated runs, and separate failed runs instead of averaging them away. Scrub auth tokens and user data from traces. Existing API timing/response breadcrumbs help but are not a complete network benchmark.

Start with launch/login, home, player list, player/clan details, current war/CWL, upgrade tracker and OTA skip. Acceptance targets should be agreed before measurements: cached navigation should remain responsive offline, stale data should be labeled, unavailable actions should explain why, and network failures must never trap the user on a loader. No honest cold-install deadline can be promised at 64 Kbps until initial payloads are reduced and measured.

### Likely improvements, in priority order

1. Reduce startup's critical requests: cached-first data, defer nonvisible detail tabs, stop eagerly fetching every account's clan/war/upgrade data, and load only the needed translation/metadata slice where the authoritative assets pipeline permits it.
2. Reduce PWA startup JavaScript through measured splitting/lazy imports; keep static release JS out of the comparison with Metro. Profile both bytes and parse cost.
3. Add correctly sized AVIF/WebP image variants and predictable cache headers. Defer decorative artwork until text/data is useful, with offline placeholders that do not repeatedly retry.
4. Introduce an explicit low-data option plus conservative automatic mode. Infer sustained poor service from actual recent request timings/failures, not merely “Wi-Fi” versus “cellular”; use hysteresis so modes do not flip on every request. NetInfo is installed, but there is no adaptive policy wired into the current app.
5. In low-data mode, lower fetch concurrency, disable speculative prefetch, request smaller images, back off background refresh and prioritize visible data. Do not silently queue purchases/account changes or hide stale war data as fresh.
6. Keep OTA escapable: the current startup changes have a five-second manifest-check escape and a small “Update in background” action. A download can continue without restarting the session after the user skips. OTA progress needs a signed release-mode test; Metro intentionally bypasses updates. [Expo: downloading updates](https://docs.expo.dev/eas-update/download-updates/)

Budget roughly 2–3 days for a repeatable harness and baseline report, then prioritize fixes from the measured request waterfall. This is a benchmark plan, not a claim that those network profiles currently pass.
